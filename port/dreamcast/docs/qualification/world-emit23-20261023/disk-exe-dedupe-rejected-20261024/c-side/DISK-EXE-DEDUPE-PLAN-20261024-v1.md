## Proposed native PowerShell transaction (NOT IMPLEMENTED OR RUN)

1. Root explicitly admits this fixed107-path inventory and canonical prefix, plus a quiet ownership window for these completed capture paths. Do not expand to newly completed paths. Take a new transaction journal using exclusive create, capture initial actual C free bytes and native filesystem volume serial. Abort if scope, file ID, size, hash or link count differs. Resolve every absolute path and every ancestor: it must remain under one exact root, have no reparse point, and name exactly flycast.exe. Revalidate RUN_COMPLETE, empty run errors, guest_exited=true, deadline_fired=false, old completion time, unchanged receipt hashes, no active bound/recorded PID of any kind, and no process executing that path. Never stop a process; skip/report instead. All current candidates are single-link, so require1again. The global console executable is neither a candidate nor a canonical source.
2. Make a NEW content-addressed directory only after root approval. Copy one admitted source into a new canonical temporary file (literal paths, exclusive creation); full hash both before/after, verify size and allocation/volume, then rename into canonical pathname. Retain the original capture untouched. Make canonical identity immutable to the transaction: no open-for-write use, future captures must continue ordinary byte-copy behavior. Readonly will apply to every hardlink; document this shared-attribute effect and set/reassert it at a proven safe point. Canonical must be on the same NTFS volume. Existing canonical adoption is a separate explicit full-hash/file-ID check, never trust its filename.
3. Before capture mutation, exercise the exact Win32/.NET atomic-replace/backup/rollback primitives on tiny disposable owned NTFS control files (separate later approval); prove byte/link-ID behavior and compatibility with read-only canonical attributes. Do not test on any capture. Prefer `[System.IO.File]::Replace(tempHardlink, originalLiteralPath, backupLiteralPath, false)` (native ReplaceFile semantics) so the original pathname remains continuously present and an original byte-preserving backup is created atomically. If metadata, sharing or read-only semantics reject the operation, leave the original unchanged and report; do not improvise a delete-first sequence.
4. Per admitted source, revalidate identity/completion/liveness. Create a unique sibling temporary hardlink to canonical using literal Win32 CreateHardLinkW (or an equivalently validated native PowerShell API); verify temp/canonical same volume/file ID and full SHA, with original still intact. Under a source read handle denying writes, atomically replace original using the temp link and a unique sibling backup. Keep original backup until all checks below pass. No cross-shell paths, cmd deletion, broad wildcard or recursive operation.
5. Verify original path now exists with canonical file ID/link count and exact source hash; canonical hash/size remains exact; backup retains original file ID and full original bytes/hash. Recheck no active PID/path. Journal all identities/results before retiring the backup. Only after these checks may `Remove-Item -LiteralPath $verifiedBackup -ErrorAction Stop` remove that one verified-identical, transaction-owned backup. Do not use blanket Force to alter shared readonly attributes. If deletion fails, retain backup, report zero saving for its allocation, and keep evidence. Never remove a source pathname or any capture/receipt/log/media.
6. Rollback before backup retirement uses atomic replacement of the canonical alias with the original backup, preserving the failed alias under another unique journaled name for review. Verify restored original bytes/file ID before touching that retained alias. Unexpected result means stop and preserve all paths, not cleanup/retry. After backup retirement bytes remain recoverable from readonly canonical; independent-file restoration would require a verified new byte copy and extra space, so preflight must preserve at least one-file rollback reserve above floor. Original allocation identity after successful dedupe is intentionally changed; original path and exact bytes remain.
7. After the admitted batch, verify every admitted original exists, hashes exact, and aliases only the pinned owned canonical; preserve all excluded paths. Verify canonical read-only and matching full hash, receipt/log/media inventory unchanged. Record final actual C free bytes and actual deleted distinct allocations; report measured delta separately from inventory potential and acknowledge concurrent external writes. If measured free space is still insufficient, stop allocation; no scope expansion, other-file cleanup or WSL shutdown follows automatically.

This is a transaction design, not a pre-cleared executor. Atomic replacement/readonly/rollback controls and root review are prerequisites. Metadata merging by ReplaceFile and shared hardlink attributes must be tested explicitly; they are not asserted from an unrun plan. Content-addressed links create shared mutable storage unless write protection and ownership are enforced.

## Alternative for root choice

Leave each admitted executable as an independent file and evaluate native NTFS per-file compression, preserving pathname/file identity and full SHA, with compression/uncompression as a separately reviewed transaction. This avoids shared-write coupling and supports reversal without deleting capture evidence. Compression ratio, observer/start cost and actual saving are not measured; no extra space is credited. This alternative is not authorized or executed by this plan. Neither alternative clears the remaining headroom deficit by assumption.
