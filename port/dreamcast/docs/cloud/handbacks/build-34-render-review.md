## 1. SCENERY_DEDUP

### Behaviour, introduction and off decision

`port/dreamcast/game/scenery19.mk` documents the modes. Mode2 reads an R4RC SCDD section, reorders eligible plain meshlet corners at room load, transforms unique grid positions and reconstructs repeated corners with each repeat's own UV/colour. Meshlets addressed through indexed pools must not be reordered. Missing or stale sections leave normal drawing. Mode2 retains the loaded room section: the comment gives about43.9KB for r101, not zero total RAM merely because there is no separate dedup allocation.

## 2. SCENERY_PIECE_STATE

`native_static.cpp` namespace `piece`, `scn21_open`, part construction and chunk replay hand off one mutable SCPS word per package part. `native_ui.cpp` checks that word as a direct index into `ps2_hdr`; it still verifies mode, texture key, logical size, live entry/key and VRAM address, then falls back to the existing set scan if the slot is stale. It is a header-cache hint, not a visibility test. SCPS slots reset to0 whenever the package is opened. Room/certificate identity checks are essential because the table is borrowed from the room file and indexed using package part numbers.

`54cef5d1560c41d074beee05ffa1ecd38f2ee642`, 2026-10-20, is the landed introduction. The message says **all default0, not in the recipe**. Piece-state with sc21 was MODELLED cross38.1→38.0ms, r10336.4→36.0ms, r100 truck37.4→36.7ms and r11b unchanged. Stills/STRICT/KOS passed within that lane; r200 had12differing pixels. The r100 movie margin fell186KB→43KB, with126KB of new r100 strip groups. This is evidence against treating the *bundled data* as free; it is not an isolated timing failure of the per-part slot hint.

`tools/d367/scenery21/scn21_build.py` does more than generate SCPS: it rewrites mesh corner/group order, creates R4SG/SCCN and recomputes SCDD. SCPS itself needs only `16+4*part_count`, padded to16, plus its R4RC directory entry. A present-day SCPS-only builder should bind unchanged current mesh CRC/bytes/count and preserve every other section. Do not carry the old bundled mesh/group replacement into an alleged metadata-only test.

The baseline `scn21_open` copies16bytes before establishing `len>=16`, uses unchecked count arithmetic and then treats the payload as aligned writable uint32 words. The Build34 sibling is implementing bounded validation for SCCN/SCPS under the existing switches; this review does **not** claim that fix is already qualified. `PS2_WORLD_HDR_CACHE=0` makes this knob's useful UI path unavailable; Make currently documents the prerequisite without rejecting0. Its strongest intended profile is cache1. PVS batch composition rejects piece-state, and the PVS opaque-proof export declines it. Build31 portal proof also declines it. These modern composition restrictions are not the historical reason it was default-off.

Owner gate: test the fixed loader's malformed/stale/misaligned/reopen cases; then exact-current-mesh SCPS-only data in both program arms. Require `SCN21 piece ... on`, increasing `PS2HDR piece_hits`, no `PS2HDR mismatched` in a separate cache2 check arm, stable room/movie/texture-eviction behaviour, current standard-program s30 floor and a reproducible console CPU saving at the barn/cross. Retain the old data bundle only as a separately labelled comparison.

## 3. TEX_PACK_WINDOW

`game/game30.mk`, `room/texture_package.cpp/.hpp` and the native UI preload pass implement a single-thread read-ahead window. It is temporary: UI requests `KB*1024+32` bytes, aligns the buffer to32, opens tex.pak once, copies package header/metadata/payload reads through it, closes it and frees the buffer after the pass. Failure to get the buffer or open the pack uses ordinary loading. The API requires at least32KiB and rounds capacity down to2048bytes. The Make gate accepts fallback2 or3, requires `TEX_PACK=1` and rejects payload CRC checking. This is a preload/I/O mechanism, not an improvement to the per-frame texture-key binary lookup.

- Introduction: `4fd6ef51ea777ae46d5a55b1f338cebcfa06171b`, 2026-10-16, default0, with `texpak_order.py`.
- Temporary recipe enable128: `52868e97b0441e1100287f9d96d89a429c9c5d85`, 2026-10-16. Weak emulated 600KiB/s +5ms/command results recorded r101 door commands1,538→403 but d09 bytes10.6→16.9MB. The same commit limits an out-of-order miss to the remaining current package instead of reading a whole speculative window.
- Explicit recipe removal: merge `359b2125bcec184b659f29a8eb3d4dab41f1ca78`, 2026-10-16, user-selected optionA. Keep fast streaming, switch permanently to plain bounded reads only after a failed read; recipe becomes `DISC_COMPAT=1 DISC_READ_FALLBACK=3 DISC_LAND_SPIN_MS=20`. `texord16` is removed from data. Use `git show -m`/blame to see this merge decision; a default non-merge pickaxe log misses it.
- Lifetime correction: `6149d57b574f59d2c4f743aab4f805bafae211e5`, 2026-10-22, extends the closed-window fallback guard to all texture formats. PAL8 host tests cover upload after closing the window. The header's “needs fallback2” comment is older than the current Make gate that also accepts3.

`CONTRIBUTING-PORT.md` explicitly leaves the window/reordered pack outside the recipe. The source now avoids the original worst speculative-read pattern, but there is no current-route physical storage win in the inspected receipts.128KiB staging plus alignment and copies can matter at low heap. Final pack layout must be regenerated after **every** texture set merge; using the old texord16 file would replace the current composition, not merely reorder it. Require same key→payload bytes, current route logs, actual read-byte/command counts, both normal stream and sticky-fallback behaviour and measured door/loading latency.

## 4. TEX_PAL32

Introduction `f58424d2208a3c6b746edfc87da5a03a81ad80d1`, 2026-10-27, is explicitly a colour-quality investigation. It reports the old truncating ARGB4444 encoding lost faint alpha and retained only4bits/channel. The runtime accepts `kPalette8888` PAL4/PAL8 tails and uploads the already-native ARGB8888 words. Unflagged packages retain their old interpretation. `tools/d367/colour27/fx_pal32.py` verifies the original palette and exact source-derived indices before rebuilding; it converted560/643private effect packages. `pal32fx27` and separate chapter2 vertex-colour candidate `ch2vc27` were deliberately not added to the recipe. Do not conflate `RE4DC_PACK_ROUND` converter opt-in or `ch2vc27` with this runtime knob.

The commit records18tests and an OFF release-image identity; `tests/test_pal32_runtime.py` currently exercises PAL4 runtime admission, distinct/shareable bank interpretation, malformed tail sizes and cleanup under ASan/UBSan. Its OFF test compares working tree with HEAD and is useful while developing a change, but after landing it is not a new historical off-vs-pre-introduction proof. The runtime also supports PAL8, whose existing general tests should be composed with flagged PAL8 cases before promoting that format.

Make strictly accepts0/1 and requires `TEX_PAL8_ALPHA=1` (which itself requires the PAL4 family). Flagged PAL4/PAL8 tails cost32/512 additional payload/VRAM bytes per texture before allocation alignment; palette RAM capacity is unchanged. Source declarations grow the PAL4 palette shadow from2048 to4096bytes, PAL8 shadow from2048 to4096bytes and add4kind bytes: **4,100 additional declared static bytes**, plus possible alignment/code/layout growth. `PalettePlan` adds4kind bytes before any compiler padding. Wider flagged palette comparisons/copies occur on load; this is not a per-frame rendering speed change. The effect appearance intentionally changes, so equality with the old truncated colours is not the acceptance criterion.

Hold for an owner colour comparison and measured RAM/VRAM affordability. Current-source full palette ownership, mip chains, sharing, exhaustion, repeated unload/reload and streamed/closed-window upload checks are needed. Do not pair a knob0 programme with widened-tail data: it correctly refuses those packages.
