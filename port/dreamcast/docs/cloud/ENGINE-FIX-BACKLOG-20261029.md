## 1. Implementation rule

**Use source and architectural reasoning to choose the correction, implement it, validate its behavior, then compare the result.** A source-demonstrated contract defect, missing native representation or repeated invariant operation is sufficient to start a bounded change. A new FPS capture is not permission to begin.

For each item, identify the intended data invariant and extend the current producer and consumer together. Preserve existing native rendering, converters, ownership/lifetime mechanisms and working kernels. The objective is a coherent evolution of this engine.

Three kinds of work have different acceptance questions:

| Kind | Why implementation can start | What the comparison decides afterward |
|---|---|---|
| Correctness/contract repair | Source exposes invalid lifetime, ambiguous completion, incomplete bounds or a concrete stale-state counterexample | Whether behavior is correct and what the repair costs. A real defect is not reinstated merely to recover its old timing. |
| Native renderer coverage | Source has a valid visual representation with no complete native route or fallback | Whether the required content is rendered correctly and how much it costs. Restoring previously missing geometry can add legitimate work. |
| Architectural optimization | Source identifies repeated immutable work, unnecessary invalidation or unsuitable data layout | Whether the new representation actually improves total cost on hardware; revise or park the optimization if it does not. |

Correct bounds, ownership, current-pose semantics and valid occluders remain implementation requirements. Hardware timing, private look checks and enabled-image acceptance follow the candidate. Retain default-off controls and disabled identity. Compile-time guards are removed only when their missing contract is implemented.

The audit's 72 groups are not 72 bugs. Required simulation, legitimate clipping, material order, explicit visual policies and correct refusal of malformed data stay intact. Generic `native_model` drawing is already Dreamcast-native; GX compatibility sinks are a separate issue. [Audit][AUDIT]

## 2. Data model to evolve

Extend the existing `Re4dcModelPart`, `Re4dcActorChunk`, `NativeDrawPlan`, texture `Entry`, world-plan and effect-queue structures. Do not create a second renderer or a new global resource manager.

| Existing boundary | Information it must carry |
|---|---|
| Asset to renderer | Encoding/version; exact spans, counts and strides for geometry/UV/color/weights; index interpretation; owner incarnation; mutation policy; validated capabilities |
| Prepared asset to draw | Immutable topology/material facts separated from current pose, camera, UV animation and live texture binding |
| Texture to compiled header | Logical material key plus the actual upload incarnation and complete effective state |
| Source adapter to native submitter | Producer identity and an outcome that distinguishes queued/submitted, culled, unsupported, refused and partial output |
| World producer to visibility | Current package/scene/view identity and completed opaque coverage, committed when the producer actually finishes |
| Native geometry to SH4ZAM | Valid bounded compatible spans and explicit matrix/FPSCR/XMTRX ownership for the complete batch |

Asset provenance and rendered coverage are distinct. A native-looking format tag does not authenticate its data, and a valid package does not prove a draw was submitted.

### 2.1 Intended end state: aligned native semantics

The destination is a coherent Dreamcast-native implementation of the selected game's visual concepts. Geometry, materials, lighting, current pose, effects, visibility and resource lifetimes must retain their required relationships across conversion, loading, preparation, drawing and retirement.

This continues the existing [PS2-inspired visual profile][PROFILE], [asset residency plan][RESIDENCY] and native cutover contracts. The running game uses recovered GameCube code as behavior/state authority, with offline-converted GC/PS2 visual inputs and native Dreamcast services. We are not importing the PS2 gameplay engine. Preserve the intended asset/rendering meaning while implementing it through current Dreamcast packages, SH4ZAM/SH-4 work and the PowerVR backend. [Current port architecture][PORT_README]

Converted PS2 animation data can supply source-selected motion while current game decisions, pose/event timing, attachments and gameplay remain authoritative. Correct format bytes and bounds alone do not establish that model/joint/material correspondence.

The sixteen items below are the first source-supported engine-fix wave. They do not certify whole-game semantic completeness. If implementation exposes a required concept that an existing native representation cannot express, extend the affected card and producer/consumer contract immediately.
