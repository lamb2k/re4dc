# Build 27: Thompson / wep12 qualification

Base: `6be0a66ab59fa597a55aae7379fb09777d357bc1` on `origin/t15/int`.
Branch: `codex/wep-modules-27-20261028`.
Control: `WEP_MODULES_27=1`, default 0.

The recovered Thompson implementation already exists in this repository.
Build 27 brings it into the Dreamcast module image through the existing
module generator, alongside the other two requested weapons. The weapon
entry, object and shared machine-gun source require **no source changes**.
The missing-module refusal and common equip transaction are described in the
combined Build 27 report and queue hand-back.

## Provenance and module boundary

|---|---|---|
| `wep12/objTompson.cpp` | [`src/wep12/objTompson.cpp`](../../../../src/wep12/objTompson.cpp) | Weapon object constructor, initialization, fire, reload, cartridges and player motion mapping |
| `wep12/pl_machine.cpp` | [`src/wep/pl_machine.cpp`](../../../../src/wep/pl_machine.cpp) | Shared machine-gun player state machine |
| `wep12/wep12.cpp` | [`src/wep12/wep12.cpp`](../../../../src/wep12/wep12.cpp) | Module entry/exit, weapon creation and callback registration |

The original unit boundaries and named functions are retained in
[`splits.txt`](../../../../config/G4BE08/modules/wep12/splits.txt) and
[`symbols.txt`](../../../../config/G4BE08/modules/wep12/symbols.txt).
Git history identifies `9c7c1181` (2026-09-10, weapon-module recovery) as the
introduction of these recovered sources. This is provenance, not a claim that
a new PowerPC binary-matching run was performed for Build 27.

The source spelling `cObjTompson` is retained. The game-facing identity is
the Thompson / Chicago Typewriter, item **0x34**, weapon **0x0C** (decimal 12), module
**56**, object-constructor slot **0x25**. The queue records module 56 as
missing from the previous executable and the resulting equip halt.

[`gen_modules.py`](../../game/tools/gen_modules.py) compiles each module's
listed units, partially links them, gathers the module's writable state and
then localizes internal symbols. This means wep11 and wep12 can each keep
their own `PlMachineMove`, `lockCtr`, helper functions and local state without
global-name collisions. It also keeps wep12's `equipWeapon` local after the
partial link. No new naming policy or common-source deduplication is added.
Only the renamed module entry/exit and the existing module-state interface
remain global under that established contract.

The generator retains its checks for unexpected module static constructors
and escaping common symbols. Fresh module linking restores writable data
and zeroes BSS through the existing platform module lifecycle. The local
owner should verify equip/switch/re-equip through that lifecycle rather than
calling a prolog alone and assuming it resets all module state.

The recovered source's empty `_unresolved` entry remains part of its REL
interface; it is not used as a substitute for any missing weapon behavior.
Required gameplay callbacks below are the real compiled functions.

## Entry, construction and archive requirements

`_prolog` registers:

- `WeaponInitFunc = Wep12_init`;
- `WeaponMoveFunc = PlMachineMove`;
- `ObjInitFunc[0x25] = ObjTompson_init`.

`ObjTompson_init` placement-constructs `cObjTompson` in the work area supplied
by `cObjMgr`. `equipWeapon` requests object 0x25 and calls its virtual `init`
with the player. Failed object creation returns null and reports the
recovered error; `Wep12_init` does not publish a new weapon pointer or load
effects in that case. The outer recovered error string still says
`Wep11_init`; changing diagnostic wording is outside this qualification.

On success, `Wep12_init` publishes `pl->Wep->m_pWep`, installs the player's
weapon motions, loads archive entry **0x04** as effect group **0x46**, and
sets the three weapon-preview aim motions to **0x1B / 0x1F / 0x21**.

`cObjTompson::init` uses model **0x06** and texture **0x05**. It clears atari
bits 8/9, parents the weapon to player part **0x0A**, sets its light area,
records item 0x34 and idle motion **0x29**, resets its motion, and installs
the recovered aim-spread settings `(5.73, 2.86, 0.2864, 0.2864)` degrees.
The shared base class performs the existing degree-to-radian conversion.
If `modelInit` fails, this method logs and returns before parenting, lighting
or motion setup. Its inherited `void init` API does not communicate that
failure back through `equipWeapon`; Build 27 does not invent a new object
initialization protocol. The requested clean refusal is for an unavailable
module, before destructive equip work.

`_epilog` clears `ObjInitFunc[0x25]` only. It does not clear
`WeaponInitFunc`/`WeaponMoveFunc`; replacement and teardown belong to the
common equip lifecycle. The fixture verifies this actual behavior rather
than expecting additional cleanup absent from the recovered code.

The pointer sanity check uses `RE4_MEM_LO/HI` from
[`types.h`](../../../../include/types.h). The existing non-PowerPC definition
already covers Dreamcast cached RAM at `0x8C000000..0x8CFFFFFF`; no wep12
pointer-range patch is needed. Routine transitions in the shared machine
source assign individual bytes, preserving the existing SH-4-compatible
routine representation. The existing `MotionMoveI` symbol alias and module
data alignment are retained; no new assembly or linker work is introduced.

## Fire, reload and player behavior

The shared `PlMachineMove` dispatches player weapon states **0 ready,
1 aiming, 2 firing, 3 lowering, 4 reload**, then performs the existing
weapon lock movement. It is the same recovered implementation used by the
other machine-gun modules, compiled into this module with local state.

| Operation | Retained behavior |
|---|---|
| Draw/ready | Motion 0x1A, camera-relative aim pitch/yaw, neck and lock initialization. The TMP-specific cocking sound is still conditional on weapon 0x0B. |
| Aim | Blend 0x1B/0x1F/0x21 for down/level/up aim; maintain laser and lock control; select firing, lowering or reload from the existing inputs. |
| One shot | Player routine calls the weapon trigger, starts 0x1C/0x20/0x22, transforms the recovered muzzle and shot line, calls `PlWepHitCheck2` with its 6,000-unit range, updates recoil and enters object fire mode 2. The shared `cObjWep::trigger` delegates actual ammunition semantics to `ItemMgr.trigger`. |
| Automatic cycle | At frame 3, held fire with rounds returns to the shot step. Empty ammunition takes the existing empty-click/aim branch; releasing aim lowers the weapon or selects the existing crouch transition. |
| Lower | Uses motion 0x1D where `dmMotCk` allows it and returns to the recovered footwork routine. |
| Reload setup | Player animation 0x1E/0x23/0x24 by reload level, knife stance and object reload mode 4. End/interrupt handling remains in the shared player routine. |

The bullet line, ammunition consumption, collision and damage service calls
are retained. These routines are not replaced by an animation-only success
path. Any special weapon ammunition policy remains in the common item/weapon
services; the test's finite ammunition values only exercise source branches.

The object fire method runs once when `wep.step == 0`. It selects recoil
motion **0x27** while rounds remain or **0x2A** after the last round; creates
flash group **0x46**; makes sound calls **2/0** and **2/0x15**; sets the shot
noise bit `Status_flg[0] |= 0x00800000`; ejects a cartridge; requests vibration
entry **0x0A**; and moves to step 1. Repeated step-1 calls do not repeat those
effects. The player routine controls when another shot begins.

Object reload uses the recovered valid reload levels 0–2:

| Reload level | Object motion | Sound, bank/index | Refill crossing frame |
|---|---|---|---:|
| 0 | 0x28 | 2 / 0x02 | 40 |
| 1 | 0x2B | 2 / 0x20 | 34 |
| 2 | 0x2C | 2 / 0x21 | 28 |

Step 0 starts the motion and sound and stores the sound handle. Later calls
invoke `ItemMgr.reload` when `MotionCheckCrossFrame` reports the chosen
threshold. The fixture checks both sides of that service result. It does not
change reload tuning or define new semantics for corrupt out-of-range levels.

Cartridges use archive **0x0A/0x0B**, a hand-local ejection offset
`(-216, -24, 105.9)`, base speed `(3, 60, 60)` with three random offsets in
`[-15, +15]`, gravity 10, radius 50 and life 40. Position and direction pass
through the current right-hand matrix. Successful shell creation attaches
effect **0x13** and marks object type 1; a refused shell allocation skips
those follow-up writes. The source does not halt for that refusal.

`setMotion` writes the recovered carry/run/turn/back/damage/knife transition
slots, clears slots 0x01/0x5D/0x5E, keeps slot 0x3D sourced from the player
archive, loads hand archive entry 0x0C and selects right hand 1 / left hand 2.
The fixture compares the full motion table against the specified writes,
including preservation of untouched slots.

## Bounded source execution

[`wep12_host.py`](../../tools/cloud/build27/wep12_host.py) compiles the complete
entry, object and shared machine source with
[`weapon_fixture_prefix.hpp`](../../tools/cloud/build27/weapon_fixture_prefix.hpp)
as a synthetic class/service boundary. Both O2 and ASan/UBSan pass **24
cases**. Receipts bind the actual source and fixture hashes:

- [Normal receipt](../../tools/cloud/build27/receipts/wep12-host.json).
- [ASan/UBSan receipt](../../tools/cloud/build27/receipts/wep12-host-sanitized.json).

The controls cover prolog/epilog and placement construction; successful and
failed object creation; model-init early return; fire with/without remaining
rounds; repeated fire-step suppression; transformed/randomized shell data
and refused shell allocation; all reload motions/sounds/crossing thresholds;
the complete motion table and hands; the player shot/collision request;
burst continuation/empty/released/crouch branches; all reload setup levels;
and ready, aim and lower entry states.

The fixture's `u32` is `uintptr_t` so host pointers survive archive arithmetic.
One `(int) this` effect-owner cast is widened to `intptr_t` in a **temporary
host source copy**. The fixture's pointer range accepts live host objects.
These adaptations do not change repository weapon sources. Mock motion,
sound, effect, item, collision and allocation services record requests and
return controlled results; they are not shipped in the image. The target
module checks use real headers, pointer widths, class layouts and generated
localization. Neither the host class layout nor mock services establish
target ABI compatibility or full gameplay acceptance.

No real archive, texture, sound bank or model data is committed or used by
the host fixture. The local owner must supply the existing weapon archive
and fixed sound bank and verify equip/fire/reload/switch behavior in Flycast.

## Size, runtime cost and disabled identity

The actual generated **SH-4** wep12 module passes compilation, partial linking,
symbol localization and the existing constructor/common-symbol checks. Its
O1 recipe matches the existing wep11 module. The
[module-build receipt](../../tools/cloud/build27/receipts/module-build.json)
records:

| Module section or stack measure | Bytes |
|---|---:|
| Executable text | 5,788 |
| Read-only data | 590 |
| Writable initialized data | 0 |
| BSS section | 28 (25 state bytes plus 3 alignment bytes) |
| Pristine initialized-data copy | 0 |
| Total allocated module sections | **6,406** |
| Largest compiler-reported local frame | 96 (`setCartridge`) |
| Prolog / epilog local frames | 4 / 0 |

These are separately linked module sections before final image placement,
not extracted game data or the host fixture's executable. The object has 84
unresolved game/runtime import names, all contained in the union already
used by admitted wep02 and wep11 modules; it introduces no new import name.
This import-closure check is not a complete game-image link. Exports match
the existing prolog/epilog plus five writable-state-boundary symbols.

The bounded target interpreter executes the actual generated module's entry
instructions with synthetic addresses for external globals; the
[entry-cost receipt](../../tools/cloud/build27/receipts/entry-cost.json)
records:

| Actual module path | Warm cycles | Cold-I cycles | Loads | Stores | Unique 32-byte lines | Observed stack bytes |
|---|---:|---:|---:|---:|---:|---:|
| Prolog registration prefix, stopping at `OSReport` | 20 | 52 | 8 | 4 | 5 | 4 |
| Full epilog | 4 | 26 | 1 | 1 | 2 | 0 |

The prolog check verifies the actual weapon-init, machine-move and
`ObjInitFunc[0x25]` callback addresses and preservation of adjacent globals.
Its cost excludes the logging body and the caller's return tail; it is not
the full prolog cost. The epilog check verifies constructor-slot clearing.
Neither entry fixture calls gameplay callbacks. Cold-I is the bounded
instruction-cache model; the listed line count is address exposure in the
fixture, not measured bus traffic or a cold-data claim.

Common module admission/equip CPU work is priced
in the combined Build 27 report with warm/cold-I cycles, loads/stores and
32-byte line exposure. Those bounded dispatcher prices exclude real archive
I/O, model creation, audio, effects and hit processing.

This qualification makes no weapon-algorithm optimization and claims no
fire/reload speedup. The enabled functional change is that a present module
can execute the recovered Thompson behavior where the previous image could
not load it; weapon modules absent from the compiled module table are refused
through the common guard. Existing fatal integrity/file/allocation failures
inside the overlay loader retain their existing policy; the three newly
enabled weapons are static modules.
No new rendering approximation, cadence, ammunition, collision, recoil or
damage policy is introduced by the wep12 sources.

`wep12.cpp`, `objTompson.cpp`, `pl_machine.cpp` and `wep_mod.h` are byte-for-byte
unchanged from this build's base. The default-off integration excludes the
new module and admission changes according to the combined target identity
receipt. No new per-frame diagnostic or test code is compiled into the game.

The queue's hand-back owns the final per-module sizes, whole-frame figure
labelled **MODELLED**, identity proof and questions for Claude. Runtime
qualification still needs real equip, held fire, empty/reload behavior,
weapon switching and re-equip after a room transition. Source fixtures and
successful compilation are evidence for those gates, not substitutes for
the local owner's play checks.
