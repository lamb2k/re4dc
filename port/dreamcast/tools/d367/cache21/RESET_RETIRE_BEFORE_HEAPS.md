# Native reset retirement before heap destruction

RESET_RETIRE_BEFORE_HEAPS defaults0 and accepts only0/1. Native enabled builds run the existing systemResetCommon after DbmenuModuleInit and before ResetDebugAlloc and MemClearAllHeap. Common restores an active borrowed UI, clears tasks, unbinds enemy/player/weapon modules and stops the room REL while their storage is alive. The motion/effect/UI room retirement trio then runs before toolmem sweeping and heap destruction. Existing per-module epilog order is retained. The late common call remains for default/explicit0/PPC/non-native builds.

Confirmed source defect: original diedemo decline can select soft reset. Its old order destroys all heaps before EmReadInit/InitModule invokes motion_unbind; release_binding reads slots and frees allocations through a captured destroyed heap handle. RESET_HEAP_FIX only wraps module Mem_free and does not repair motion_free. An active UI also needs restoration while its room heap exists. Room effect binding5 is outside common module cleanup, so moving common alone is insufficient. Placing the new phase before ResetDebugAlloc also keeps tagged source/tool allocations alive through cleanup. RoomData.restartRelData normally links the kept module and copies BSS; it performs no normal DVD read here. DLL failure/HALT and missing-prolog overlay fallback remain their own preconditions.

Actual reset-function host qualification uses common and soft-reset bodies extracted from the candidate, compiled under ASan/UBSan in six variants. The native-enabled12 cases cover loaded/empty state, UI open/closed and module-pin/motion/effect/UI refusal. Refusal halts before tool sweep or heap destruction and preserves unreleased owners. The baseline/default/explicit0/PPC-enabled/non-native-enabled preprocessed functions are exact. Matching reset-keep fields and cleanup ordering are checked. Platform I/O, allocation and fatal functions are test seams; this is source/host control flow, not actual target allocation or a game-crash reproduction.
