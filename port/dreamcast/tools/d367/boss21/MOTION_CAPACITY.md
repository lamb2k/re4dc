# Reclaimable motion capacity candidate

Base: `d4a3b31fac3362937a3f21eaa874e07be94fd061`. Isolated branch `codex/boss21-motion-capacity`. `MOTION_CAPACITY=0` is the default; `=1` requires the existing packed reserve/backing path and pressure cap. This is a review candidate, not production integration or whole-game acceptance. QA audio recovery is excluded. The eight H062 lifetime/failure edges remain OPEN.

## Mechanism and bounds

The K05 em11 working set is 22,400 + 32,416 + 17,408 = 72,224 bytes. Its unchanged joined reservation holds 64,832 bytes; physical SDK heap free/largest is 83,168 bytes. The original 131,072-byte castle margin correctly prevents ordinary spill. Packing alone cannot retain this set.

When packed storage cannot fit a v2 cold clip, the candidate may allocate an optional, reclaimable overflow payload. The existing aggregate heap-key payload cap remains 262,144 bytes. Slab count/size, strict v3 two-cell admission, record format, relocation, CRC/FNV checks, source evaluator, animation rate and geometry stay unchanged. A fixed 32-byte bitmap per binding marks only this new overflow, plus its original SDK owner. No slot expansion, permanent reserve or new package is introduced. Allocation failure falls back to the established reserve policy; failed reads never publish a slot or marker.

`mem_alloc` and `Debug_alloc` retry a failed heap4 SDK request through the motion owner before their final failure result/diagnostics. The reclaimer takes the motion mutex, drops only unpinned marked overflow, and retries the exact SDK request before unlocking. The source block therefore owns the recovered gap before cache refill resumes. Existing hot keys and slab backing are not reclamation victims. A waiter counter prevents new speculative overflow while requests drain. Pointer addresses never move.

If only another thread's overflow pins remain, the reclaimer releases the mutex and yields for their finite evaluator scopes. It retains the existing cancellation owner across both mutex contention and pin waits. Cache-internal metadata/reserve admission uses the already-held mutex and SDK-only reclaim/retry, without a recursive lock, native allocation or pin wait. IRQ exclusion surrounds actual SDK allocation/free list mutation and the native high-cell list mutation; no reclamation, allocation callback, I/O or waiting occurs inside those guards.

Normal unbind/room retirement frees overflow through its true `MotionAllocation` base and owner. Source heap4 destruction drains new overflow first; the all-heap path does so before ancestor destruction. Retirement prevents refill until a newly admitted archive. Existing hold/suspend refuses reclamation, and dead-heap slot forgetting clears the corresponding marker. A movie owner's staging request retains recent-use resume tickets; unrelated background requests during a movie do not become movie tickets.

## Source contract and remaining limits

The seven current lease scopes are `MotionSetCore`, `MotionMoveCore`, `MotionGetSpeed`, `MotionGetPosition`, `CalculateShape_new`, `CameraMotion` construction and `CameraMotion::move`. IK setup precedes the first lease. The leased portions perform key/parts/table, Hermite, vector/matrix and attach-camera-table work. Parts/error logging uses the preallocated log ring; it does not call the SDK allocator. The fixed Hermite decoder dispatch, camera orientation and selected direct helpers were reviewed. `motion-capacity-source-contract.json` pins the reviewed scopes and direct call names; these are source-review guards, not a formal transitive callgraph proof.

The source DVD destination allocation is in `cDvdQueue::readInit` outside the native synchronous DVD read/callback scope. `dvdread_callback`, `cb_dvd_read_end` and `gcci_rd_cbfn` only update state or do nothing. Shared storage consumers perform CRC/copy/VRAM upload, with allocation outside their reader lock. The hand job allocates under its own mutex; motion transport does not acquire that mutex. Selected AICA/ARQ storage uses KOS/AICA memory; the selected AXFX hooks are ignored stubs. KOS allocation is a separate heap.

The following are **not cleared** by this candidate:

- A same-thread evaluator allocation or IRQ/interrupt-masked required request cannot wait. The hook declines instead of deadlocking or freeing a live pointer. None was found in the reviewed selected evaluator/callback paths; a future or unresolved transitive caller must be reviewed before claiming universal allocation feasibility.
- Hold/suspended-heap reclamation and a held reset are deliberately refused. The existing reset/borrower lifetime findings remain OPEN; this candidate does not repair or certify them.
- Native static reserve/high-placement preflights can decline before reaching `mem_alloc`. Their admission policy is not equivalent to a failed required SDK request and remains a named followup. The optional SS_POOL_TOP path has an ordinary `mem_alloc` fallback. OSAllocFixed/AddToHeap have no selected gameplay callers in the source inventory.
- New optional overflow uses explicit heap4 rather than the shared CurrentHeap. Existing CurrentHeap switching and general concurrent heap destruction/suspension are still source contracts, not established by the short SDK list guards. The eight H062 ownership/failure findings remain independent.
