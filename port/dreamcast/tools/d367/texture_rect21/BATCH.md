These owned offline tools prepare an unselected private cohort from the sealed remaining756 inventory. They do not edit runtime tables, frozen worlds, a programme, a full texpack, or an image.

`batch_next.py` applies the existing horizontal 2:1 opaque RGB565/VQ/source-flags0 contract in four dimension classes. `nearest64.c` is a host-only accelerator with exact int64 nearest-vector arithmetic and first-index tie rules; the constructor's default Python engine is unchanged. The batch runs shared C/Python vector and full-package representative controls, then independent C decodes for every generated mip level. Its compact base remains a filtered/requantized approximation. Normalized periodic UVs retain scale1,1.

The reviewed next415 invocation uses a fresh private output directory containing only `nearest64.so` and an empty evidence directory:

```

python3 batch_next.py --out "$OUT" --evidence "$EVIDENCE" --library "$OUT/nearest64.so"

```

The actual Package gate builds two shared sanitizer-enabled host readers from the real Package/storage sources with explicit filesystem/PVR stubs. Strict adopt and streamed CRC1 acceptance are tested for the entire ON cohort; OFF rejection and legacy-CRC/corruption/truncation controls are separate. Host tests do not establish PVR appearance, real GPU residency or Dreamcast acceptance.

World proposals replace only selected key pairs and the physical body CRC. Meshes, placements, pass, cull, texture indices (including valid index0), and all other material bytes are preserved. The combined representation table and provenance certificates are proposals only. Each new room needs its complete runtime policy, physical ownership/profile and lifecycle contracts closed before selection. In particular the known r107 AREA baseline CRC/table mismatch and r11f/r200 physical ownership guards are not solved by a generic policy-CRC mapping.
