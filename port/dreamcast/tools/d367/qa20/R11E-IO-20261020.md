# r11e pre-fight animation I/O

The original QA Test 21 program reproduces the reported slowdown before the
El Gigante encounter. This is independent of the menu-close watchdog defect.
The tester also reports that the slowdown follows the yellow disc-read icon.

The exact final QA GDI was reused without changing its program or game data.
Its boot payload matches the retained qa20W ELF; all fourteen overlays match.
The QA menu selected the original r11e entry. No menu was opened during play,
and no enemies, events, health, positions or timers were edited.

An initial 50-second Flycast run temporarily reaches 30 fps, then falls below
2 fps. The saved state is live r11e, source frame 706. A second 50-second run
continues that exact program and state with a read-only process observer:

| Observation | Start | End | Difference |
| --- | ---: | ---: | ---: |
| Source frame | 706 | 817 | 111 |
| Animation misses | 26 | 193 | 167 |
| Animation loads | 25 | 192 | 167 |
| Animation evictions | 24 | 191 | 167 |
| Physical disc reads | 1,564 | 4,575 | 3,011 |

The recurring animation working set is Ashley's entries 0, 6 and 61: 5,152,
5,056 and 448 bytes. They cycle through the original `pl11-r11f` profile's
two reserved slots. The archive is 384,064 bytes with 69 external cold clips.
The motion payloads are small, but opening them repeatedly also traverses the
35-sector `/dc/mot` directory. KOS has sixteen inode-cache sectors; the retained
and live cache show repeated sequential directory sweeps. Late windows record
about 61 physical reads per second and about 950 ms of blocked time per second.
Music reads are zero in those windows. Texture loads remain fixed at 139.

These are **Flycast observations**, not console timings. The read-only observer
validates the owned process path and creation time, verifies five original boot
program anchors in the saved RAM, and reads the exact ELF's local cache symbols.
No hardware CPU-cache diagnosis is inferred.

The existing `pl11-hot` offline profile already describes this same 0/6/61
cycle, formerly observed in castle rooms. It retains eight recurring near-enemy
clips in the archive, preserving their source data and the rest of the bounded
cache. The regenerated body is 411,744 bytes and matches the existing typed
runtime admission: table CRC `3913017b`, body CRC `eb2fce03`. All three cycling
clips are now resident rather than external cache records. This changes no
geometry, textures, AI, animation rate, collision or event logic.

The corrected candidate changes only the `pl11.drs` payload: 1,742 other disc
files, the original boot program and all fourteen overlays are identical.
Regenerating the original source wrapper also restored raw GC audio and caused
one sound allocation failure in the first diagnostic candidate. That candidate
is rejected and retained as a control. The corrected wrapper appends the same
admitted native body to the currently qualified wrapper; every existing byte
outside its native-payload header, including the prebuilt AICA bank, is preserved.
`reuse_hot_ashley.py` reproduces it from explicit hash-checked private inputs.

The corrected 51.1-second cold-start Flycast run reaches source frame 886 without
the original sustained collapse. It has three animation misses/loads and one
eviction in total, rather than 167 additional misses/loads/evictions in the
original 111-tick continuation. The recurring three source clips stay resident.
Normal owned-window forward/back input produces approximately 1,015 world units
of displacement and returns near the entry, with unchanged health and room phase.
One newly used movement clip causes a single 10-read, 146-ms load; the following
window is quiet. Most late windows report 29.9 fps and 100% source speed; this is
an emulator observation, not a hardware timing or whole-fight qualification.

The corrected Ashley bank loads as the original prebuilt 8-kHz, 68,064-byte bank.
Sound failures remain zero. Texture loads stay at 139; VRAM free remains
1,015,424 bytes, with zero rejects, retries, evictions or refusal counters.
The prepared native body grows by 27,680 resident bytes. Its transport wrapper
grows further on disc because the original unreferenced payload is retained;
those old wrapper bytes are not an extra runtime motion allocation.

A 50.8-second continuation of that exact state advances source frame 886 to
2,357 with six normal forward/back actions, then an idle interval. Physical
reads increase only from 1,120 to 1,121: one 8-KiB read logged with 0 ms blocking.
Animation loads increase from three to four and evictions from one to two, then
remain steady through the end. The final 28 seconds have no additional physical
reads. The recurring three-key eviction cycle does not return. Health, room,
phase, sound and texture failure counters remain unchanged. Final source-speed
windows show 29.9 fps / 100% in Flycast. Both saved-state checks validate five
original boot anchors; the final state SHA-256 is
`bd7f8a9b8ef4736c61d6411830ba604c2cb5e970370478f2cf15149aa5796781`.

This qualifies the narrow pre-fight emulator regression, including the tested
movement. Full encounter, castle-room working sets and physical Dreamcast
confirmation remain separate gates. The corrected private wrapper SHA-256 is
`c3817d66b62478003e720e3439c858c08cb0c952fdca8e96ab0bc2604723d2c0`.
The original QA package is unchanged. The separate heartbeat repair is on
`codex/qa21-r11e-debug`; it does not by itself address this slowdown.

The policy audit is broader than the r11e proof. `native_motion.cpp` admits the
strict version-3, two-reserved-slot/no-spill policy only for three exact rows:
Mendez module61 (82 external clips, body1,035,392), old Ashley module47
(69/384,064), and hot Ashley module47 (61/411,744). Other version-2 archives use
reserved slots plus heap-margin-guarded spill/cold allocation and pressure LRU;
the QA build resolves spill margin524,288, cold margin262,144 and pressure
cap262,144. They can still thrash under pressure or with a larger active set.
The r11e result therefore clears the tested Ashley entry, not all characters,
objects, castle rooms or the Mendez encounter.

For each room/action sequence, the existing `MOTION_STATS_LOG` reports misses,
evictions, bytes, residency and heap4 margin per disc window. `MOTWS` reports
per-archive window/five-window/bind working-set counts and bytes;
`MOTION_MISS_LOG` attributes individual misses to archive size, entry, bytes and
wait. Both diagnostics are off in the original QA program. An exact-symbol,
owned-process read-only observer was used here to retain original-program
identity. Repeat the same bounded room/action observation and correlate
physical disc reads with repeated clip keys before changing another profile.
Cache policies or archive labels alone do not prove a room has or lacks churn.
